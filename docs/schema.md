# Warehouse Schema

The warehouse is a star schema in PostgreSQL database `retail_dw`. One fact table holds the sales lines. Three dimension tables describe them: date, customer and product.

## Fact table: `fact_sales`

**Grain:** one row per invoice line, meaning one product on one invoice. Every measure is defined at this level.

| Column | Type | Notes |
|---|---|---|
| `sales_key` | INTEGER, identity | Generated key. Part of the primary key. |
| `invoice_no` | TEXT | Invoice number. Cancellations start with `C`. |
| `invoice_date` | TIMESTAMP | Partition key. Kept here because PostgreSQL partitions need the column in the table. |
| `date_key` | INTEGER, FK to `dim_date` | |
| `customer_key` | INTEGER, FK to `dim_customer`, nullable | NULL for sales without a customer ID. |
| `product_key` | INTEGER, FK to `dim_product` | |
| `country` | TEXT | Stored on the fact because the source records it per invoice. |
| `quantity` | INTEGER | |
| `unit_price` | NUMERIC(10,2) | |
| `line_total` | NUMERIC(12,2) | `quantity * unit_price`. |
| `is_cancelled` | BOOLEAN | True for invoices starting with `C`. |
| `has_nonpositive_quantity` | BOOLEAN | True for zero or negative quantity. |

Primary key: `(sales_key, invoice_date)`. The partition key has to be part of the primary key.

## Dimension tables

- **`dim_date`**: `date_key` (identity), `full_date` (unique), `year`, `month`, `day`, `weekday`.
- **`dim_customer`**: `customer_key` (identity), `customer_id` (unique, NOT NULL).
- **`dim_product`**: `product_key` (identity), `stock_code` (unique), `description`, `category`. Categories are `product`, `gift_voucher`, `service_fee` and `adjustment`.

Surrogate keys (`*_key`) are generated by PostgreSQL. The source IDs are kept as natural keys, so the warehouse does not depend on the source's numbering.

## Why a star schema

- Each report joins the fact to one dimension at a time, which keeps queries simple.
- Totals scan the fact once and join only small dimension tables.
- Most BI tools expect this shape.
- The dimensions are small, so repeating their attributes is cheap compared with the fact table.

Alternatives considered: a snowflake schema (more normalized, more joins, little saving here) and one flat table (repeats descriptions and categories on every row, and makes changes expensive).

## Partitioning

`fact_sales` is partitioned by RANGE on `invoice_date`, with one partition per calendar month, from `fact_sales_2010_12` to `fact_sales_2011_12`, plus `fact_sales_default` for any date outside those months.

Why monthly: the reports and the archive both work by month. Queries for one month read one partition, and an old month can be detached and archived without touching the rest.

The partitions are created by `warehouse.py`, covering the months present in the data. Partitions do not create themselves, so a new month needs a partition before its data arrives. The rebuild each run handles this.

## Indexes

| Index | Column | Used by |
|---|---|---|
| `idx_fact_sales_product_key` | `product_key` | Reports by product or category. |
| `idx_fact_sales_customer_key` | `customer_key` | Reports by customer. |
| `idx_fact_sales_date_key` | `date_key` | Reports by day or weekday. |

PostgreSQL creates these on every partition automatically. Date filtering does not need its own index, because partition pruning already limits the rows read.

Measured effect (see [query_plans.md](query_plans.md)): a single-customer lookup takes about 1 to 10 ms with the index and about 107 ms without. The product and date lookups show the same pattern: 10.5 ms against 83 ms, and 7.2 ms against 110 ms. Aggregations over most of the table are not helped, because the planner reads the whole table faster than it could use an index.

## Materialized view: `mv_monthly_revenue`

Monthly revenue by month and country, excluding cancelled invoices. It is rebuilt by `performance.py` on every pipeline run.

Measured effect: 0.13 ms from the view, compared with 932 ms from the fact table for the same answer.
